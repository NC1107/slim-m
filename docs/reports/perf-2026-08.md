# Performance report, 2026-08

The performance story had gone stale: the last committed server baseline was `0.15.0`, twenty-three releases behind the `0.38.0` this pass measured against, client cold start and memory had never been measured at all, and the Voice Canvas's own spike-era benchmark machinery had never been run at its documented target object counts and written down.
This report closes all three, with exact commands and the hardware they ran on, so the next reader does not have to re-derive any of it.

## Hardware and environment

Every number below was taken on the same machine, in one sitting, on 2026-08-13.

- AMD Ryzen 9 9950X3D, 8 logical CPUs visible to this environment (the host box is a 16-core part; this sandbox is capped to 8), 30 GiB RAM.
- Fedora Linux 44 (KDE Plasma), kernel `7.1.6-201.fc44.x86_64`.
- `rustc 1.94.1`, `Dart SDK 3.12.2`, `Flutter 3.44.8` (stable channel), `Google Chrome 151.0.7922.75`.
- This box runs several unrelated agent sessions concurrently, per this project's own standing note about it; nothing here was taken in exclusive control of the machine, which is a real source of the noise recorded below rather than a hypothetical one.

No number here is a clean-room, dedicated-hardware reading, and none of the sections below claim otherwise.

## 1. Server idle and peak RSS, and the criterion hot-path benchmarks

**Fresh baseline committed: `perf/baselines/0.38.0.json`**, following `perf/README.md`'s own methodology (median of five runs; see that file for why RSS needs several readings rather than one).

Commands, run from the repo root:

```sh
SQLX_OFFLINE=true cargo build --locked --release --bin slimm-server
for i in 1 2 3 4 5; do bash perf/measure-idle-rss.sh; done
SQLX_OFFLINE=true cargo bench -p slimm-server
```

`measure-idle-rss.sh` builds and runs the musl image from the committed `docker/server.Dockerfile` for the musl half, so this needed Docker and nothing else beyond what the two commands above already state.

| metric | 0.8.0 | 0.15.0 | **0.38.0 (this pass)** | budget (STRATEGY.md) |
|---|---|---|---|---|
| idle RSS, glibc | 7,296 kB | 8,748 kB | **9,756 kB** | under 30,720 kB (30 MB) at true zero load |
| peak RSS, glibc | 25,760 kB | 26,916 kB | **27,272 kB** | - |
| idle RSS, musl | not measured | 5,924 kB | **6,828 kB** | - |
| peak RSS, musl | not measured | 24,080 kB | **24,748 kB** | - |
| `uuid_now_v7` | 119.57 ns | 118.96 ns | **118.50 ns** | - |
| `version_json_serialize` | 134.98 ns | 138.71 ns | **134.63 ns** | - |

The five raw idle-RSS readings this baseline's median came from (kB): glibc `9768, 9644, 9936, 9756, 9540`; musl `6828, 6872, 6844, 6768, 6792`.
Both hot-path benchmarks are flat across three releases spanning about a month of real feature work, which is the expected shape for a benchmark measuring UUIDv7 generation and a small JSON serialize: nothing in that path has changed, and nothing should have moved it.

Idle RSS has grown by roughly 2,460 kB (glibc) and 904 kB (musl) since `0.15.0`, over twenty-three releases that added, among other things, the whole canvas write path, the moderation queue, space analytics, and notification sounds.
That is real growth, and it is nowhere near the 30 MB zero-load budget: `0.38.0` sits at 9.76 MB idle on glibc, less than a third of the ceiling, with 20+ MB of headroom before this needs attention.

Not re-litigated here: `perf/README.md`'s own reasoning for why this stays a manual, by-hand measurement rather than a CI gate (a virtualized runner is a third environment, not a stand-in for either a real deployment or a contributor's own machine).
That reasoning was re-read before this pass and still holds; nothing here changes it.

## 2. Client cold start and idle memory

**No number existed for this before this pass**, for either platform this environment can reach.
What actually got measured, and why, needs stating plainly before the numbers: this is the client's **web build**, driven headless, standing in for the Linux desktop build STRATEGY.md's own budget table names.

### Why the web build, not the Linux desktop build

The Linux desktop target links GTK, and GTK needs a display connection to construct a window even to run fully offscreen.
This host has neither `Xvfb` installed nor passwordless `sudo` to install it - checked directly rather than assumed:

```console
$ rpm -q xorg-x11-server-Xvfb
package xorg-x11-server-Xvfb is not installed
$ sudo -n true
sudo: a password is required
```

The job brief's own fallback for exactly this case is to measure the web build's metrics via CDP instead, and say so honestly rather than presenting it as the native number.
This is that: a real, headless `google-chrome-stable` process opens no window on this or any display, which is what makes it a legitimate stand-in for "offscreen," not a workaround for the "never a visible window" rule.
The web build's numbers are dart2js-compiled JS plus CanvasKit/Skia WASM booting inside V8, not the Linux GTK embedder's own native startup path, and the memory figure is a Chrome tab's resident memory rather than a native process's RSS.
Both are read as what they are below, not represented as the native Linux figures STRATEGY.md's table was written against.

### Method and command

`scripts/measure-client-startup.sh` builds the web release, serves it locally, then for each of 3 runs launches a fresh headless Chrome against a fresh profile and measures, over the Chrome DevTools Protocol, through the new `scripts/lib/client_startup_probe.py`:

- **Cold start**: wall time from process launch to the moment Flutter's own accessibility tree has real content - the same signal `scripts/lib/e2e_client.py`'s `enable_semantics()` already uses to know the app is up, since that only happens once the engine has booted and painted the first real screen. This probe configures no server, so that first real screen is onboarding.
- **JS heap**: `Performance.getMetrics`' `JSHeapUsedSize`, after a 5s settle.
- **Process-tree memory**: the **Pss** (proportional set size) of the whole process tree the launched Chrome spawns, summed from `/proc/<pid>/smaps_rollup`, not `VmRSS`. This mattered in practice, not just in theory: Chrome's processes share large mappings (its own binary, the V8 snapshot, ICU data), and summing plain `VmRSS` across a zygote, a GPU process, a network-service utility process and several renderer helpers reported **1.3 GB** of "memory" for a bare `about:blank` tab with nothing on it - an implausible number that the code comment in `client_startup_probe.py` records verbatim as the reason `Pss` is used instead.
- **A same-flags `about:blank` baseline**, per run, so headless Chrome's own fixed per-process cost can be told apart from the app's own - the same control this project's Space analytics section used for a server measurement.

```sh
bash scripts/measure-client-startup.sh --runs 3
```

### Results

| | run 1 | run 2 | run 3 | median |
|---|---|---|---|---|
| cold start (interactive) | 687 ms | 719 ms | 657 ms | **687 ms** |
| JS heap | 24,671 kB | 27,375 kB | 24,686 kB | 24,686 kB |
| JS heap over an idle Chrome tab | 24,199 kB | 26,903 kB | 24,214 kB | 24,214 kB |
| process-tree Pss | 561,312 kB | 605,868 kB | 560,560 kB | 561,312 kB |
| process-tree Pss over an idle Chrome tab | 159,317 kB | 203,768 kB | 159,421 kB | **159,421 kB** |

STRATEGY.md's Linux client budget is cold start under 1.2s and idle memory under 200 MB.
Read honestly rather than as a pass/fail against that table: 687 ms of dart2js-and-CanvasKit boot time is comfortably under the 1.2s figure, and 159 MB of Chrome-tab memory over an idle tab's own baseline is under the 200 MB figure - but neither is the thing that budget was written to bound, and this report does not claim the Linux desktop budget is met.
What it does establish is a first real, reproducible number where none existed, and a documented, repeatable way to get another one the day `Xvfb` is available or a Mac/device lab can run the native build.

## 3. Voice Canvas fps and memory, at the roadmap's own target counts

`docs/ROADMAP.md`'s Phase 5 deliverables name the target object counts explicitly: roughly 5,000 on iOS, 20,000 on Linux.
Four benchmark files already existed under `client/packages/voice_canvas/benchmark/` from the Phase 5 spike; none of the four had been run against a fifth, `canvas_memory_benchmark.dart`, which this pass wrote because none of the existing four measured memory at all.
All five ran clean on this pass; every number below is from this run, on this box, on 2026-08-13.

### 3.1 Spatial index query cost (`spatial_grid_benchmark.dart`)

AOT-compiled first, for numbers that resemble a release build rather than the JIT harness's own numbers - the file's own header recommends this:

```sh
cd client/packages/voice_canvas
dart compile exe benchmark/spatial_grid_benchmark.dart -o /tmp/spatial_grid_bench
/tmp/spatial_grid_bench --json
```

Frame budget is 16.6 ms (60fps). At the two target counts, `hotspot` world shape (the busiest realistic distribution the spike's own harness models), zoom 1:

| | grid query | linear-scan control | grid, % of frame budget |
|---|---|---|---|
| n=5,000 | 3,699.5 ns | 6,224.1 ns | 0.02% |
| n=20,000 | 14,980.0 ns | 25,264.7 ns | 0.09% |

Both are trivial against the budget, consistent with `docs/research/canvas-spike-server.md` and `canvas-spike-client.md`'s own original finding that a plain scan is already cheap at these counts and the index earns its place past them.

Two of the spike's own findings were re-checked at `0.38.0` rather than assumed still true, and both still hold:

- **The adaptive linear-scan fallback at extreme zoom-out is still load-bearing.** At `n=20,000`, `hotspot`, zoomed out to see the whole world (`zoom=0.001`), the plain grid query alone costs **11.87 ms - 71.5% of the frame budget**, a near-miss. The adaptive path (falling back to a linear scan once cell span exceeds object count) costs **71.9 us - 0.43%**. Without it, a person zooming out on a busy canvas would visibly drop frames.
- **1024px is still the right cell size, not the originally planned 2048px.** Sweeping cell size at `n=20,000`: `256px` costs 17.2 us, `512px` costs 12.1 us, `1024px` costs **10.5 us (the minimum)**, `2048px` costs 15.2 us, and it gets steadily worse past that (`4096px` 70.9 us, `8192px` 142.6 us).

### 3.2 In-flight remote stroke paint cost (`remote_draft_paint_benchmark.dart`)

Run via `flutter test` (needs `dart:ui`, so the plain Dart VM harness above cannot host it):

```sh
cd client/packages/voice_canvas
flutter test benchmark/remote_draft_paint_benchmark.dart
```

| drawers | points/draft | paint cost | % of frame budget |
|---|---|---|---|
| 1 | 8 | 0.003 ms | 0.0% |
| 1 | 660 | 0.015 ms | 0.1% |
| 6 | 8 | 0.007 ms | 0.0% |
| 6 | 660 | 0.090 ms | 0.5% |
| 20 | 8 | 0.021 ms | 0.1% |
| 20 | 660 | 0.301 ms | 1.8% |

660 points is the file's own stress case: three seconds of continuous drawing at the client's `maxStrokePreviewPointsPerFrame` cadence, with nothing capping how long an in-flight draft may grow before its `ended` frame arrives.
Even 20 simultaneous drawers at that stress shape cost under 2% of one frame; this is not close to a bottleneck at any realistic call size (STRATEGY.md's own call-size figure is 2-8).

### 3.4 Riverpod-vs-ChangeNotifier hot path (`hot_path_benchmark.dart`)

```sh
flutter test benchmark/hot_path_benchmark.dart
```

| | cost |
|---|---|
| `ChangeNotifier.notifyListeners` | 16 ns |
| Riverpod `StateProvider` dispatch | 199 ns (12.6x) |
| recull + notify, 1 object | 59 ns |
| recull + notify, 20,000 objects | 626 ns |
| `pump()` harness floor | 23.87 us |
| repaint-only path, over floor | 79.19 us |
| Riverpod rebuild path, over floor | 163.99 us |

Confirms the spike's own architectural finding still holds: the off-Riverpod `ChangeNotifier` hot path is roughly an order of magnitude cheaper per dispatch than routing the same update through Riverpod, which is why the canvas's render loop is built the way `canvas_pane.dart`'s own module doc insists on.

### 3.5 Resident memory at the target object counts (`canvas_memory_benchmark.dart`, new)

None of the four existing benchmark files measured memory - they all time the spatial index and the paint layer, never what a real `CanvasDocument` costs to hold.
This is new: it builds a real `CanvasDocument`, places objects at the two target counts (a 32-point stroke each, well under the ~256-point length `stroke_splitter.dart`'s own module doc names as roughly where an encoded stroke nears the server's byte ceiling), and reads the `flutter_tester` process's own resident memory (`dart:io`'s `ProcessInfo.currentRss`) before and after - the same "read the real process" preference `perf/measure-idle-rss.sh` already takes for the server.

```sh
cd client/packages/voice_canvas
flutter test benchmark/canvas_memory_benchmark.dart
```

Run three times, since a single RSS reading is exactly the kind of number `perf/README.md` already warns against trusting on its own:

| | run 1 | run 2 | run 3 | median |
|---|---|---|---|---|
| baseline (empty document, engine loaded) | 125,064 kB | 124,848 kB | 125,172 kB | 125,064 kB |
| total at n=5,000 | 148,880 kB | 149,164 kB | 148,304 kB | 148,880 kB |
| total at n=20,000 | 161,308 kB | 163,120 kB | 160,816 kB | 161,308 kB |

Reading this as a per-object cost is where the noise actually lives, and it is worth stating plainly rather than smoothing over: the delta from baseline to 5,000 objects is roughly 23.8 MB (**~4.9 KB/object**), but the delta from 5,000 to 20,000 - fifteen thousand more objects - is only another ~12.4 MB (**~0.85 KB/object incrementally**).
That is not the shape a linear per-object cost would produce.
It is Dart's generational garbage collector growing its own heap arenas in chunks well ahead of what is immediately live, so the first few thousand objects "pay for" slack capacity the next several thousand then use for free - the same caveat `perf/README.md` already states for the server's RSS ("page-cache timing, what else the host is doing"), one layer further in, at the allocator rather than the OS.
An earlier, less-settled run of this same benchmark (not the numbers reported above, an initial check while writing it) read 14,756 kB and 21,268 kB for the same two deltas - visibly different, same machine, same code, back to back.
Treat the totals in the table as the real, repeatable numbers; treat any single incremental "bytes per object" figure computed from one run as noise, not a constant.

Both totals are well inside the budget the client memory figure has to fit under alongside everything else the app holds (STRATEGY.md's 200 MB Linux idle-memory line is for the whole app, not the canvas alone): 20,000 objects, past the Linux target count, adds roughly 36 MB over the bare engine's own footprint.

## Wiring into `perf.yml`

**Nothing new was added to the CI workflow.** Each measurement above was checked against whether it belongs there, not skipped by default:

- **The criterion Rust benchmarks** are already wired (compile-only on every PR touching `crates/**` or `perf/**`, a real run on every release) and untouched by this pass.
- **Server idle/peak RSS** was already, deliberately, not wired in, and this pass found no reason to revisit that: `perf/README.md`'s own stated reasoning (a virtualized CI runner is a third environment, not a stand-in for a real deployment or a contributor's own machine) is unchanged by anything found here.
- **Client cold start and idle memory** inherits the identical reasoning, doubly: on top of the noisy-host problem RSS already has, this measurement adds network timing (fetching two gitignored WASM/JS assets), V8 GC timing, and a full Chrome multi-process launch, none of which a shared runner makes more deterministic than this box already is.
- **The four existing canvas benchmarks, plus the new memory one, stay unwired for their numbers, but their compile-safety is already covered for free.** `client-ci`'s existing workspace-wide `dart analyze` step already type-checks every file under `benchmark/`, including the new one - confirmed directly, not assumed: a deliberately broken constructor call (`bogusParam: 1` in place of a real named parameter) in `canvas_memory_benchmark.dart` was caught immediately by a plain `dart analyze` run naming the exact file and line, with the file restored byte-identical afterward. That already closes the actual failure mode a new compile-gate job would exist to catch - this benchmark machinery silently bit-rotting against the production API - on the existing schedule, at zero added CI cost. What a new job would add past that is asserting on the benchmarks' own numbers, and `canvas_memory_benchmark.dart`'s own run-to-run variance in this same report (the n=5,000 delta over baseline ranged 14,756-24,316 kB across independent runs on identical code, on one dedicated box - a swing of roughly 65%) is exactly the kind of reading a shared, virtualized, contended CI runner would make worse, not better - the same shape of flaky, falsely-authoritative gate `perf/README.md` already declined to build for the server.

## What is still not measured

Named rather than left to be assumed done:

- The Linux **desktop** build's own cold start and idle memory, which needs either `Xvfb` (or equivalent) on this box or a run on hardware that already has a display.
- iOS cold start, idle memory, and active-call memory - needs a Mac and a device, neither available here, the same limit every other iOS-only surface in this client already carries.
- The aggregate egress bandwidth budget and active-call memory budgets STRATEGY.md names, which need several real clients in a real call at once; `docs/ROADMAP.md` already names `scripts/e2e.sh` as the obvious thing to grow into that.
- LiveKit's own idle/voice-room/video-room RSS budgets (STRATEGY.md's separate SFU line), out of this pass's scope.
