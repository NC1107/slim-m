# What slim-m does today

This is an inventory of the product as it actually stands, derived by reading the server's route table (`crates/slimm-server/src/http.rs` and `http/*.rs`, gated against `schema/openapi.yaml`) and the client's screens, routes, and providers, not by reading the planning docs.
`docs/BRIEF.md`, `docs/STRATEGY.md`, and `docs/ROADMAP.md` describe the product that was planned; this describes the product that exists, as of server 0.26.0 and client 0.24.3 (`.release-please-manifest.server.json`, `.release-please-manifest.client.json`).
`CLAUDE.md` is closer to the ground truth than the planning docs but stops at 2026-07-31; a lot has shipped since, including threads, message replies, calling in a DM, markdown, message jump, drag-to-reorder channels, an actionable report queue, image paste, and a canvas eraser and undo.
This file is meant to be re-derived the same way, not hand-maintained by memory.

## What it is

From `docs/BRIEF.md`: a lightweight, cross-platform, open source messaging platform with optional self-hosting, recreating the core Discord experience (group chats and direct messages with text, voice, and screen sharing) rather than cloning it feature for feature, with an infinite collaborative Voice Canvas during calls as the signature feature.
It ships as a Flutter client (iOS, Android, Linux) talking to a single Rust server process with an embedded SQLite database, plus a separate stateless Go push relay that only wakes backgrounded mobile clients.
One deployment is one community: there is no multi-tenant hosting and no federation between deployments.

## Capabilities today

Every item below says where a person actually reaches it from, not just that the server has a route for it.
Where the reachability trap this project has hit before (an endpoint with no call site) mattered, it's called out.

### Talking

- **Channels and DMs.** Text channels, voice channels, and direct messages, all `channels` rows distinguished by `kind`. A DM with yourself renders as an ordinary DM titled "You" rather than a special-cased channel, reached from the rail like any other conversation.
- **Threads.** `docs/decisions/0005-threads.md`: a thread is a channel with a `parent_message_id`, not a separate table. Opened from a message's context menu ("Reply in thread") or from the "N replies" affordance under a message that already has some, both routing to `/thread/:channelId`. Permissions, sync, push, and search all fall out of a thread just being a channel; nesting a thread inside a thread is refused server-side (400). A live socket event (`ThreadUpdated`) keeps the reply count and last-reply time fresh for anyone already viewing the parent.
- **Replies.** A message can quote another message inline (`messages.replyToId`); tapping the quote jumps to the original. This is the lighter mechanic threads were built beside, not a smaller version of them.
- **Reactions, pins, polls.** Reactions are per-viewer filtered (a blocked reactor's tally is invisible to you, and reactor identity is never on the wire). Pins are a moderation action gated on `MANAGE_MESSAGES`, capped at 200 per channel, refused rather than silently truncated past that. Polls are single-choice, 2 to 4 options, sent as a message rather than a separate resource.
- **Search.** Per-channel full-text search (SQLite FTS5) over that channel's messages, supporting FTS5's own mini query language (`AND`/`OR`/`NOT`, `"phrase"`, a trailing `*` prefix). There is no cross-channel search and no advanced operators (`from:`, `in:`, `has:`, `before:`/`after:`, `filename:`); that's a backlog item, not built.
- **Markdown.** Bold, italic, strikethrough, and spoilers inline; headings, quotes, and ordered or bulleted lists as blocks. No toolbar: it's typed markers (`**bold**`) plus keyboard shortcuts (Ctrl/Cmd+B, Ctrl/Cmd+I), with Enter continuing a list and closing it on an empty item. Hand-rolled parser rather than a markdown package, because the existing mention chips, custom emoji, and inline code widgets predate it and a document-rendering package can't produce them.
- **Message jump.** Search results, pinned messages, the command palette (`Ctrl+K`), and the report queue all navigate to a message and flash-highlight it, through one shared function rather than four separate implementations.
- **Edit, delete, and message reconciliation.** Edit and delete are authorship-gated (edit also allows `MANAGE_MESSAGES`). An edit that changes nothing writes no history and shows no "(edited)" marker. A separate op stream (`message_ops`) makes edits and deletes made while a client was offline actually reconcile on reconnect, closing what used to be the project's oldest correctness debt; a client upgrading through this crosses one forced cache wipe to get there.
- **Attachments and image paste.** Attachments are content-addressed by sha256 for dedup, sniffed from bytes rather than trusted headers. Image paste into the composer works differently per platform: confirmed working on a real iPhone via the system long-press edit menu with no permission prompt; a "+"-sheet fallback row exists on both iOS and Android (Android's route is unit-tested only, not confirmed on real hardware); the web build listens for the browser's own paste event; desktop (Linux, and macOS/Windows if built) has no clipboard-image handler at all and falls back to the file picker.
- **Custom emoji and reactions.** A searchable, grouped, keyboard-navigable emoji picker mixing the deployment's custom emoji with a recents shelf. Custom emoji upload is `MANAGE_SERVER`-gated.
- **Read state and unread.** Own-device read markers sync through `/sync`; unread counts are derived on demand rather than separately counted. Read receipts visible to other users are deliberately not built (owner decision, deferred).
- **Command palette and shortcuts.** An in-app-focused quick switcher (`Ctrl+K`) and user-remappable keyboard shortcuts, both reachable from any screen.

### Voice, calls, and the canvas

- **Voice channels.** 1:1 and group voice plus screen share over a self-hosted LiveKit SFU. A join preview shows who's already in the room (roster, mic pre-toggle, and now a camera pre-toggle) before you connect; nothing auto-joins.
- **Calling in a DM.** Landed 2026-08-01. No new route and no per-DM room provisioning: a DM channel is a channel, so it only needed `CONNECT`/`SPEAK` added to the permissions a DM's two participants already hold. Reached from a phone/call icon in the DM's header (both the wide and compact layouts), which swaps the conversation body for a call pane wrapping the same voice screen a real voice channel uses. There is no ringing: nothing pushes a wake for an incoming DM call, so both people effectively have to already be looking at the app.
- **Screen share.** Works, with two platform-specific traps worth knowing rather than a flat "it works": on Linux it needs a `sourceId` matched against enumerated screen sources, and enumerating *windows* (not screens) on Wayland segfaults the process, so that path is never called; on iOS the fix (forcing manual track publication so the ReplayKit extension and flutter_webrtc don't both try to start a capture) is reasoned from LiveKit's own source and unit-tested, but has not been confirmed on a real device.
- **Per-participant volume.** Works on Android, iOS, and macOS. Throws on Linux and Windows (a flutter_webrtc limitation: those platforms never populate the map the lookup depends on). Silently does nothing on web (there's no handle to a remote track's audio element to apply gain to). The slider is hidden on platforms where it wouldn't do anything, including Linux, which is one of the project's two local dev and test targets.
- **Camera.** Capture works with a pre-toggle before joining. Background blur or replacement does not exist; the owner has called it close to a requirement, not a nice-to-have, but it needs a per-frame segmentation model and hasn't been started.
- **The Voice Canvas.** More built than the last written snapshot (2026-07-31) suggested. A shared collaborative pen: place strokes (`POST /channels/{id}/canvas/objects`), erase your own or, with `MANAGE_CANVAS`, someone else's (`remove`), clear the visible canvas (`clear`), and undo (`restore`, an inverse op rather than rewriting history). A timeout freezes the pen but never the eraser, so a timed-out member can still remove their own ink. Still absent: moving or resizing an object (the store function exists but has zero HTTP callers), pasted images or GIFs, camera bubbles, screen-share tiles, and multi-user cursors. Whether a canvas is meant to be permanent per channel, a per-call artifact, or something cleared by hand is an open product question (`docs/OPEN-QUESTIONS.md`); the schema only expresses "permanent per channel" today, which is what's shipped.
- **Android voice.** Declared its `RECORD_AUDIO`/`CAMERA` permissions only recently and has never had a call held on real hardware. Treat the whole Android call path as unverified rather than working.

### Identity and onboarding

- **Accounts.** Standard account creation on the official instance; invite-link or invite-code creation with no email on self-hosted servers. Three onboarding entry points (join official, redeem invite, connect to a self-hosted address), with an explicit server-identity fingerprint confirmation step for a manually entered address (trust-on-first-use, not active MITM protection) and a terms-of-use acceptance step at invite redemption.
- **Multi-device.** A day-one requirement, not a retrofit: per-device sessions, refresh-token rotation with reuse detection, and instant revocation from the device list.
- **Account deletion.** Self-service, purges personal data, tombstones the account, and revokes every session. Refuses if you're the last administrator and other members remain (409), which is the only thing standing in for "ownership transfer" (there is no ownership model in the schema to transfer). There is no admin-initiated deletion of someone else's account.
- **Presence.** Online/away/DND/offline with an appear-offline option, told apart by shape rather than color alone. Presence for a channel follows whether you can view that channel.
- **The capability handshake.** `GET /version` reports which safety-relevant capabilities (report, block) a server actually exposes, derived by probing the real router rather than a hand-kept list, so a fork that strips moderation can't silently claim to have it. The sign-in screen warns if they're missing or if the server is too old to say; it never blocks the connection.

### Moderation

- **Roles and permissions.** A 63-bit bitmask, 15 bits defined today (`ADMINISTRATOR`, `VIEW_CHANNEL`, `SEND_MESSAGES`, `MANAGE_MESSAGES`, `MANAGE_CHANNELS`, `MANAGE_ROLES`, `KICK_MEMBERS`, `BAN_MEMBERS`, `CREATE_INVITE`, `ADD_REACTIONS`, `ATTACH_FILES`, `CONNECT`, `SPEAK`, `USE_CANVAS`, `MANAGE_CANVAS`, `MANAGE_SERVER`). Evaluated as `@everyone` base, then role union, then channel overwrites (role-tier deny wins, member overwrite absolute), then the `ADMINISTRATOR` bypass. A roles screen and a per-channel overwrites screen are both reachable from Space settings, gated on `MANAGE_ROLES`.
- **Timeouts and removal.** A timeout subtracts most permissions (but deliberately not `USE_CANVAS`, so a timed-out member can still see and erase, just not draw) and force-evicts them from any live voice call, since a LiveKit token can't be revoked once minted. "Remove from Space" is a durable ban (`space_removals`, reversible from a removed-members screen), gated `BAN_MEMBERS`; it does not stop a fresh account on an open Space.
- **The report queue.** Genuinely actionable now, not list-and-dismiss. A moderator can jump to the reported message, delete it (`MANAGE_MESSAGES`), time out the author (`KICK_MEMBERS`), or remove them from the Space (`BAN_MEMBERS`), each action closing the report; each is absent, not just disabled, when the caller lacks the bit. Self-targeting is excluded. The queue itself is pre-filtered by channel visibility before pagination, so a short page always means a short page.
- **Drag-to-reorder channels.** `MANAGE_CHANNELS`-gated, deployment-wide (one order for everyone, since one deployment is one community), optimistic with a visible revert on failure.
- **Invites and channel management.** Invite creation, revocation, and a check that answers expired/spent/revoked/never-issued identically (so codes can't be mined) are all reachable and `CREATE_INVITE`-gated. Channel create/rename/delete is `MANAGE_CHANNELS`-gated; deleting a deployment's last non-DM channel is refused (409).
- **What's not there.** No browsable, searchable admin user list or bulk user actions; the closest thing is the ordinary member list everyone can see plus the per-member popover (timeout, remove, assign role). No admin-facing metrics or diagnostics endpoint (`/metrics` does not exist anywhere in the router). Admin-issued one-time password reset codes are the only account-recovery mechanism; there's no recovery email by design.

### Safety

- **Blocking.** Filters at read time on the client (a blocked author's messages still sync but never render), not at fetch time, because filtering `/sync` itself would make "unblock" unable to bring anything back. Reactions and push notifications are filtered server-side, per viewer, since neither of those can be filtered on-device. A blocked DM says so in the composer and offers Unblock rather than rendering as an empty, unexplained transcript.
- **Reporting.** Any member can report a message or a user, with a 2000-character reason cap shared between reporting and moderation. Feeds directly into the actionable report queue above.
- **No automated content or media scanning.** Owner decision: safety is manual reporting plus the tooling above, not proactive scanning. The official instance's own legal obligation (report known CSAM to the relevant authority on discovery, no proactive monitoring) is documented in `docs/decisions/0001-owner-decisions.md`, with no separate implementation artifact beyond that document.

### Self-hosting

- **Deployment.** One production `docker-compose.yml`: server (embedded SQLite on a named volume), Caddy for automatic TLS, LiveKit for voice, and an optional Litestream sidecar. Litestream replicates the SQLite file only; attachment and avatar bytes are not covered, and restoring a Litestream replica brings back message text and attachment *references* but not the files. There is no `VACUUM INTO` backup-and-restore drill built yet, only the Litestream path.
- **CORS.** Opt-in via `SLIMM_CORS_ALLOWED_ORIGINS`; unset means no CORS layer at all, not an empty one; a wildcard origin is refused at startup.
- **Attachment storage ceiling.** `SLIMM_MAX_TOTAL_ATTACHMENT_BYTES` has no default (an operator's disk size isn't something the software can guess); past it, uploads fail with a 507 rather than a 413, so an operator can tell "the volume is full" from "your file is too big."
- **Push notifications.** Content-free, encrypted, relayed through a separate stateless Go service that only forwards to APNs/FCM and never sees plaintext. Registration and the lifecycle (foreground/background) signal are both wired on iOS and Android. What's still missing: an iOS Notification Service Extension. There is exactly one iOS app extension target and it's the screen-share broadcast extension, not a notification one, so an iOS push still shows a generic "New message" rather than decrypted content. Android device wake has never been confirmed on real hardware either; both device-wake exit criteria from the original plan remain open.
- **Platforms and packaging.** iOS (TestFlight) and Linux (rpm, published to Fedora COPR) are the two platforms actually built and tested day to day. A Flatpak manifest still doesn't exist, so that half of "Linux artifacts" never ships despite being planned since Phase 0. Android builds and ships to Play's internal testing track but has no confirmed real-device call path. A web build exists, compiles, and is gated in CI as of the most recent fix, but it's explicitly excluded from v1 scope in `docs/STRATEGY.md` and is used here mainly as a fast way to drive the app in a real browser for testing, not as a released target. macOS and Windows desktop are not built at all.

## What's deliberately not built

From `docs/STRATEGY.md`'s v1 scope and `docs/BACKLOG.md`'s "deliberately out of scope," with the reason each time, so a reader knows these are absent on purpose rather than missing:

- **End-to-end encryption.** Transport-only (TLS) for v1; the server holds plaintext. Per-user and per-device keys are pre-wired so opt-in E2EE DMs can be added later without a wire-format rewrite. Full E2EE was rejected because it breaks history, search, sync, and server-side moderation, and the self-hosting trust model already puts the operator inside the content boundary.
- **Federation between deployments.** One deployment is one community; DMs only work between two people on the same deployment. Not Matrix- or ActivityPub-style federation, and not planned to become that.
- **Multiple communities under one backend.** Same reasoning; revisited only if self-hosters actually ask.
- **Read receipts visible to others.** Deferred as a later opt-in; your own read state already syncs across your own devices.
- **Rich presence and game status**, a **soundboard**, a **client plugin/scripting system**, a **slash-command framework**, **server-side link unfurling**, an **events/RSVP subsystem**, and **scheduled recurring pings that store PII** are all recorded declines, each because it drifts toward being a Discord clone or opens a real security or maintenance surface the product doesn't need. Webhooks and a future bot API are the sanctioned extension point instead of a plugin system.
- **Heavy ML noise suppression.** WebRTC's built-in echo cancellation and noise filter are used instead, to avoid a native DSP/ML dependency taxing CPU during a call.
- **Automated content or media scanning.** Manual reporting only, by owner decision; see Safety above.
- **A shared media gallery view.** Not built, but cheap to add later since it's only a filtered query over the existing attachment store.

## Where it stands against the roadmap

`docs/ROADMAP.md` is itself annotated with correction passes through 2026-07-28, and some of what it still calls open has since closed; some of what it calls closed was oversold at the time.
Reading the code rather than the annotations:

- **Phases 0 to 3 (foundations, server core, client shell, push).** Solid. The one real gap that survives every correction pass is the iOS Notification Service Extension: still not built, confirmed directly against `project.pbxproj` for this document rather than assumed from an adjacent note that only proved the *technique* (manual extension target creation) works, not that the NSE itself exists. Android push wake has never been confirmed on hardware.
- **Phase 4 (voice and screen share).** Built and reachable, including the DM-calling extension the roadmap didn't originally scope. Two things the roadmap's exit criteria ask for are still unmeasured rather than unmet: the aggregate egress bandwidth budget and active-call memory budgets have never been measured, and "works on real Fedora/iOS hardware" rests on partial device confirmation, not full.
- **Phase 5 (canvas de-risking spike).** Done for object counts and the R-Tree viewport query; flicker-free media culling near the viewport boundary was never spiked, which matters less now that Phase 6 has shipped real production code anyway.
- **Phase 6 (canvas full build).** Further along than "not started" or "a first slice" (the roadmap's own last two labels): place, erase, clear, and undo are real, permission-gated, and reachable from a toolbar. Still missing every other Phase 6 deliverable: move/resize/z-order, images and GIFs, camera bubbles, screen-share tiles, compaction, the bitmap cache, and the accessibility fallback log. No convergence property test exists.
- **Phase 7 (administration, moderation, metrics).** The moderation half is well past what the roadmap credits it for: the report queue went from list-only to fully actionable, and threads, reply counts, and channel reordering all shipped as administration-adjacent features the roadmap doesn't name. The metrics half named in this phase's own title is untouched: no `/metrics` route, no time-series store, nothing.
- **Phase 8 (audio and polish).** Reduce-motion and the desaturated-presence proof are done. The synthesis pipeline exists and produces seven distinguishable sounds, but nothing plays them yet: no per-platform playback, no CallKit ringtone, no CI bundle-check.
- **Phase 9 (release readiness).** Not met, as expected this early. No `VACUUM INTO` backup drill, no Flatpak, and the project still carries its placeholder name. Server and client are both comfortably pre-1.0 (0.26.0 and 0.24.3), and `bump-minor-pre-major` is deliberately keeping it that way so a breaking change doesn't accidentally tag a 1.0 nobody chose.

The overall shape worth taking away: messaging (talking, threads, replies, moderation) has outpaced its own roadmap language, voice has grown a DM-calling capability the plan never named, the canvas is meaningfully past "first slice," and the two areas where the roadmap's "not built" is still exactly right are the iOS Notification Service Extension and admin-facing metrics.
